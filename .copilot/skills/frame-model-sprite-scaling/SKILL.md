## Facts
- Models **ignore frame size**; only `BlzFrameSetScale` changes how big they look. The guide's example comments say "Models don't care about Frame Size, But world Object Models are huge. To use them in the UI one has to scale them down alot" and that the size "does not matter but has to be there" (it uses 0.00001 and 0.01).
- World-object models are huge. Tasyen's Dec 4, 2019 reply in the 3D Model thread: "Unit models are huge, to have them fit on the screen one has to scale them down to a small fraction. In Reforge Beta they are displayed in not black mode." The thread's original poster (xorkatoss) posted a SPRITE at `0.2 x 0.2` with no scale whose active model line was `ui\\feedback\\xpbar\\xpbarconsole.mdx` (the Arthas line was commented out) and reported "the whole screen turning black". The thread does not say which model caused it, and Tasyen's reply addresses unit-model size only. Inference: an unscaled model covering the screen is the likely cause. The right scale is **model specific**: Tasyen used `0.002` for a unit model and `0.00006` for `RockBoltMissile` (size 0.01).
- Overlay on a button: scale = `buttonWidth / 0.039` (default command button size) with `BlzFrameSetAllPoints(button)`.
- SPRITE loops its animation automatically. Indices through `BlzFrameSetSpriteAnimate(frame, index, 0)`: birth 0, death 1, stand 2, morph 3, alternate 4. A Jun 5, 2025 comment by wiselen (not Tasyen) says the native supports more tokens than these five and links an external quick reference; that was not verified here.
- STATUSBAR does not loop; `BlzFrameSetValue` maps the percent of min/max to the animation time. The guide says "It is said" STATUSBAR only supports 1 s animations (sequences after 1 s are dropped), and TriggerHappy saw units using the same model as the bar affected by the bar's current animation. In the guide's ModelBar example the frame size is tiny (0.00001, "does not matter but has to be there") and the scale is 1 for the UI model `ui/feedback/progressbar/timerbar.mdx`.
- `BlzFrameSetParent` can bug SPRITE (speeds up its animation) in 1.31. Do not reparent after creation.
- `BlzFrameSetScale` can break custom fonts on text frames; scale after creation, not at it.
- MODEL frames report mouse events only on their screen space, not on the visuals.

## Choosing the frame type
- Use **SPRITE** for unit/doodad models. Every example found that renders one creates a SPRITE under `ORIGIN_FRAME_GAME_UI` (or `ORIGIN_FRAME_WORLD_FRAME`) with inherits `""`: Tasyen's 3D Model on UI and RockBoltMissile recipes, Rigborn's UI: Adding Sprite, wiselen's sprite-rotation sample. Rigborn adds that without TOC files loaded you create the SPRITE with `BlzCreateFrameByType("SPRITE", ...)`.
- **MODEL**: no source found shows a world model rendering in one, at any scale. Tasyen (Jun 2019): "One needs to create a Frame of type "MODEL" or "SPRITE", cause you want the frame to be animated you should use "SPIRTE"" [sic], adding that he knew of no published native for controlling such a frame's animation. When rolandc85 (Jun 2019) got a fully black screen from a MODEL frame showing an unscaled Footman at `0.2 x 0.2`, Tasyen answered "That needs special 2d models. (Edit: In Warcraft 3 Version 1.31.1)" with `ui\\feedback\\xpbar\\xpbarconsole.mdx` as the example (edited Nov 27, 2019). Tasyen's FDF notes call MODEL an "Unanimated model of the Frame Family" and SPRITE a "non-Interactive Frame displaying a Warcraft 3 model and loops its animation".
- Version caveat (source-backed dates, inferred meaning): the "special 2d models" statement is explicitly tagged 1.31.1, while Tasyen's working Footman recipe is from the Reforge Beta (Dec 4, 2019, "they are displayed in not black mode"). Whether the 1.31.1 MODEL restriction still applies on the current patch is not stated anywhere I found, and whether MODEL (not SPRITE) can show a unit model on any patch is unverified.
- Inference (not stated by any source): if `ModelFrame` + a unit model stays black while `SpriteFrame` + the same model renders, MODEL cannot display world models; use SpriteFrame for those.
- **STATUSBAR** with a UI model: size `0.00001`, scale `1`, `BlzFrameSetValue` drives the animation. In Tasyen's Dec 2024 and Mar 2025 posts `ui/feedback/progressbar/timerbar.mdx` is the active line, and `ui/feedback/cooldown/ui-cooldown-indicator.mdx`, `ui/feedback/XpBar/XpBarConsole.mdx` and `ui/feedback/buildprogressbar/buildprogressbar.mdx` are commented-out alternatives.
- `inherits` (the 4th argument of `BlzCreateFrameByType`) is the FDF template, not the frame type. Passing `"SPRITE"` there does not create a SPRITE.
- `BlzFrameSetSpriteAnimate` is reported to work only on SPRITE and STATUSBAR (wiselen's crib; reverse-engineered, version unspecified), so `ModelFrame` does not call it.

## Call order is not the cause of a black screen
Working examples use different orders: Tasyen's 3D Model on UI: model, size, scale, point. Rigborn's UI: Adding Sprite: point, size, scale, model. wiselen (Dec 2025): point, size, model, scale. The Animated Model Frames sample: clear points, point, size `5 x 5`, model, with no `BlzFrameSetScale`; its author says the shipped model "took me about 8 hours to perfectly fit on the screen", i.e. the model itself was fitted instead of scaled. Inference: what the working examples share is a model that fits the screen (by `BlzFrameSetScale` or by editing the model), not a call order.

## Known rendering problems
- Unit models appear top-down: X maps to screen width, Y to height, Z to depth, and no native rotates a sprite (wiselen, Dec 2025). Fixes from the sources: add a helper bone as the parent of the root bone and rotate it, or add a one-frame global sequence that rotates it (FeelsGoodMan, 2022; Elprede in UI: Adding Sprite), or edit and reimport the model (TriggerHappy). Rotating the vertices directly breaks animations (FeelsGoodMan). Without editing the model, wiselen tried an FDF `Camera {}` block: on Dec 6, 2025 the camera coordinates had to be thousands of times larger than in portrait models, geosets flickered through the depth buffer, and scaling the sprite also scaled the camera position. His Sep 15, 2026 follow-up says "the FoV value needs to be specified in degrees, not radians" and shows an FDF with `CameraFieldOfView 66.667`; it does not say whether the flicker is gone.
- Models with their own camera: try other `cameraIndex` values. Indexing is undocumented ("you have to try which one works", Rigborn). TriggerHappy (2022): such models "show but have some odd bugs such as being unable to scale or position them properly".
- Particle emitters, glow and huge geometry can cover the whole screen: remove the particle emitters (Rigborn) or scale the model down "a tremendous amount" (FeelsGoodMan, for the Flying Machine).
- Black or white model parts: Rigborn says they come from shading and from `HeroGlow`/`TeamColor` texture layers. His fix is to save the model as MDL in Retera's Model Studio, change `Teamcolor00` and `TeamGlow00` to `01` (up to about `23`), and set the material layer to unshaded, then import that model.
- UI model support is limited: only certain animations work, with no timescale control, rotation, or attachments (TriggerHappy, Apr 25, 2020).
- Frotty's guide notes that `setVertexColor` works on model/sprite frames and that reparenting a SPRITE can permanently speed up its animation.
- Unresolved report (no answer in the thread): Gaspar's SPRITE under `BlzGetFrameByName("ConsoleUIBackdrop", 1)` with `BlzFrameSetAbsPoint(0.4, 0.6)`, scale `0.80`, `UI\\Glues\\MainMenu\\WarCraftIIILogo_exp\\WarCraftIIILogo_expbeta.mdl` and no `BlzFrameSetSize` call "doesn't show up" (post 3521562, Feb 9, 2022, on Tasyen's [Frame Buttons](https://www.hiveworkshop.com/threads/frame-buttons.337943/)). Tasyen's reply above it (Reforged 1.32+) says frames under `ConsoleUIBackdrop` escape the 4:3 limit but draw below SimpleFrames. Inference: the missing size call is the most likely cause, since the Big Tutorial's model examples say size "has to be there"; the thread does not confirm it.

## Repo pattern (src/components/MonoFrames/model.ts)
- `scale`, `width`, `height` are configuration properties; the fallback literals (`0.002`, `0.001`, `0.001`) live in `DefaultConfiguration`.
- Default render position is 0.4, 0.3 (see [frame-creation](../frame-creation/SKILL.md)).
- Expose a scale updater so the scale can be tuned per model.
- `ModelFrame` creates `FrameType.Model`; `SpriteFrame` creates `FrameType.Sprite` and also calls `BlzFrameSetSpriteAnimate`. Use `SpriteFrame` for unit/doodad models.

## Test harness (src/debugging/frame-component-test-harness.ts)
- `NativeFrameFeatureTest.standalone` creates the frame directly under the harness owner (`ORIGIN_FRAME_GAME_UI` by default) with inherits `""`; `toggleTest` then only does `clearPoints` + `setAbsPoint(FRAMEPOINT_CENTER, 0.6, 0.38)`, the point set last like Tasyen's example. The other native tests go through `createNativeFrameTest`, which wraps the frame in a container, re-anchors it with `setPoint` and calls `setSize` after the scale; no working example does that.
- Standalone tests: Model page "Set Footman model" and "Set XP bar model", Sprite page "Set Footman sprite". The "Create bare type" tests stay in the container so the label confirms creation.
- Do not pass a frame type as `inherits` (an earlier test passed `"SPRITE"` that way).
- "Set Footman model" uses Tasyen's 3D Model on UI values on a MODEL frame. "Set XP bar model" uses `ui\\feedback\\xpbar\\xpbarconsole.mdx` (the model Tasyen names for MODEL frames) at scale `1`, borrowed from his STATUSBAR example rather than from a MODEL-specific source. Caveat: the 3D Model thread's original poster had this same model active on a SPRITE at the default scale and reported a black screen, so this test may also fill the screen.
- Reading the results (inference): Sprite Footman renders but both Model tests stay black means MODEL cannot show these models here, so use `SpriteFrame`. All three black means the wrapper, the model path or the scale needs another look. None of this has been verified in-game from this repository.
